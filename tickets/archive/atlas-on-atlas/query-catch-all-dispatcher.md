## Why

Surfaced by the first §11 retrospective on the `identity/tenant-admin-invites-user` slice (2026-05-21). The slice needs `GET /api/v1/identity/memberships` to render the Users surface. The query (`listMemberships` in `modules/identity/src/queries.ts:80`) exists. The route binding does not — it would need a hand-mount in `apps/server/src/routes/identity.ts`. That's an apps/server edit → kernel touch by §11.1 row 2.

The retrospective made a genuinely new finding: **`always-on.md` §6 Phase 1's "action-driven catch-all via `controlPlaneRegistry`" is intent-side only**. There is no parallel query-side catch-all. Every read endpoint today is hand-mounted in `apps/server/src/routes/*.ts` — `catalog.ts`, `content-pages.ts`, `authz.ts`, the seven identity routes, scim, oauth, saml, etc. Each new read endpoint is a kernel touch that ought to be a module edit.

This ticket is the extraction-plan target for that retro. It ships the missing substrate: a `QueryRegistry` port, a `<moduleName>QueryRegistry` export per module (matching the existing `*HandlerRegistry` shape), a single catch-all in `apps/server/src/routes/queries.ts`, and an example migration of one existing read endpoint to prove the substrate. Once this lands, the identity slice's `listMemberships` exposure is a one-line module edit (register in the identity query registry) and no longer fires §11.1.

This is also a stronger statement of `always-on.md` §6 Phase 1 itself — the phase as currently written ("Action-driven routing — replace hand-wired `app.route(...)`") is silent on queries. This ticket either amends Phase 1 to cover both sides, or adds a Phase 1b that does so, with the substrate ticket below.

## Scope

In scope:

- Spec amendment to `always-on.md` §6 (intent vs query catch-all — explicit) and `architecture.md` if needed.
- New port `QueryRegistry` in `ports/src/query-registry.ts`. Shape: `{ register(queryId, fn): void; get(queryId): QueryFn | undefined; list(): ReadonlyArray<QueryDescriptor> }`. Mirror `HandlerRegistry` deliberately.
- Per-module query registries — one file per existing module (`identity`, `catalog`, `content-pages`, `authz`). Each module exports its registry from `src/index.ts`.
- Single catch-all route in `apps/server/src/routes/queries.ts` mounted as `GET /api/v1/queries/:queryId`. Reads the queryId, looks up via composed query registry, runs against per-request `QueryDeps`, returns JSON.
- `apps/server/src/middleware/state.ts` composes the four module query registries the way it already composes handler registries.
- **One example migration** — pick a small existing read endpoint (e.g., `/api/v1/catalog/families` or similar) and migrate it from hand-mount to the catch-all. Keeps this ticket's scope bounded; bulk migration of all read endpoints is follow-up work.
- Integration test that registers a synthetic query, calls it via the catch-all, and asserts the answer comes through without any `apps/server` route file edit.

Out of scope:

- Migrating every existing read endpoint — one example only. Bulk migration is per-module follow-up tickets.
- Authorization-on-read changes — query-side authz already runs at ingress per existing pattern; the catch-all uses the same path. No new authz code.
- Cache key / cache invalidation contract changes — queries continue to use the existing per-query cache contract.
- The intent-side catch-all (`§6 Phase 1`) — that's its own ticket and is not blocked by this one.
- `atlasctl query list` / parallel I17 surface — flag as follow-up if not in this ticket; depends on how aggressive scope is.
